# Candidate Applications for the `llm-c4-controls` Control Set

Mapping the 41 control components in this repo (C4 Level-3 diagrams `04-data-exposure-controls.puml`
and `05-agent-tool-runtime-controls.puml`) to real software that can *implement* each
control — open-source and commercial — with a completeness verdict.

Generated by parallel research across 7 control clusters, then synthesized. Research
artifacts (per-cluster tables) sit alongside this file:
`candidate-apps/access_control_tools.md`, `candidate-apps/ai-control-candidates.md`,
`candidate-apps/ai_data_security_control_candidates.md`, `candidate-apps/agent_safety_controls_tooling.md`,
`candidate-apps/supply_chain_controls.md`, `candidate-apps/ai_post_usage_controls.md`,
`candidate-apps/injection_screening_tools.md` (re-dispatched).

## Completeness scale

Every control gets one verdict:

| Verdict | Meaning |
|---|---|
| **Full** | Mature OSS/commercial tool(s) implement the control as a turnkey or near-turnkey capability. |
| **Partial (repurpose)** | Real tooling exists but you must repurpose generic infra (policy engine, KMS, gateway, sandbox) and wire it yourself. |
| **Partial (composite)** | Capability exists only as a *stack* of 2–4 tools composed together; no single product covers it. |
| **Emerging / build** | No off-the-shelf product; you build it or assemble immature/early-stage components. |
| **None** | No known candidate. |

### an_dlp — AI-DLP / pre-redaction scrubber (PII removed BEFORE egress to model) · `LLM02, LLM04`
**Verdict: Full (classic PII) / Partial (semantic).** Regex/NER DLP is mature and turnkey; semantic leakage is not caught by any classic tool.
- **OSS:** Microsoft Presidio (canonical self-host), scrubadub.
- **Commercial:** Google Cloud DLP / Sensitive Data Protection, Azure AI Language PII, Amazon Comprehend, Private AI (on-prem), Nightfall, MS Purview.
- *Gap:* Cloud APIs themselves require egress (defeats the "before egress" point unless self-hosted). All classic tools miss paraphrased/semantic leakage — that is `post_dlp`'s job.

### an_rbac — Field-level RBAC on the case/log store · `LLM03`
**Verdict: Partial (repurpose).** Generic data-access controls, not AI-native.
- **OSS:** OpenSearch/Elasticsearch Field-Level Security, OPA data-filtering, Cerbos, OpenFGA, pgvector+Postgres RLS.
- **Commercial:** Snowflake dynamic masking, AWS Verified Permissions, MS Purview / Varonis.
- *Gap:* These gate the *store*, not the model's reasoning over it; you bind them to the analyzer's read path.

### an_inj — Ingested-content screener (hidden instructions in logs/alerts) · `LLM01`
**Verdict: Partial (composite).** Detection is decent; inline *prevention* before summarization is a wiring job. *(filled by re-dispatched research — see §injection row below)*

### an_out — Output redactor before analyst view · `LLM10, LLM02`
**Verdict: Full (flag) / Partial (redact).** Many tools *flag*; fewer *redact* in-line.
- **OSS:** Microsoft Presidio, GuardrailsAI Output Guards, Llama Guard (classifier, not redactor), NeMo Guardrails.
- **Commercial:** Azure OpenAI Personal-Information filter, OpenAI Privacy Filter (open-weight, new), Private AI, Nightfall.
- *Gap:* Some only flag; true redaction-in-path needs Presidio/Private AI wired before render.

## 2. Private-data exposure — Tokenization & model diagnostics (LLM02, LLM08, LLM06)

### tok_scrub — Pre-scrub PII before third-party tokenizer · `LLM02, LLM04`
**Verdict: Full (no-egress options exist).**
- **OSS:** Presidio, scrubadub, Faker (synthetic substitution).
- **Commercial:** Private AI (on-prem container). (Cloud PII APIs partly defeat the purpose.)
- *Gap:* Streaming latency at tokenizer scale unverified.

### tok_gate — Gate logprobs & internal model states · `LLM02, LLM08`
**Verdict: Partial (repurpose).** No tool natively strips logprobs from responses; you enforce via gateway/policy.
- **OSS:** LiteLLM Proxy (virtual keys restrict who can *request* logprobs), vLLM / TGI (don't expose internal endpoints by default), OPA (sidecar: "only operator may call /logprobs").
- **Commercial:** Kong AI Gateway, Azure API Management, AWS Bedrock IAM, Cloudflare AI Gateway (response-transform to strip fields).
- *Gap:* None auto-strip logprobs from model output; you write the policy/transform. `unsure` on vLLM per-key suppression.

### tok_rl — Rate-limit & cap (token inflation / homoglyph stuffing) · `LLM06`
**Verdict: Partial (repurpose).** Gateways throttle requests/tokens, but *token-density / payload stuffing* inspection is custom.
- **OSS:** LiteLLM Proxy (rpm/tpm/max_parallel per key/user/team), Apache APISIX, Envoy + RL service, vLLM/TGI per-key limits.
- **Commercial:** Kong AI Rate Limiting Advanced, Cloudflare AI Gateway, AWS Bedrock quotas, Azure API Management.
- *Gap:* No native adversarial token-stuffing detector; build a payload inspector. `unsure` on rich tenant caps.

## 3. Private-data exposure — Semantic Search (LLM02, LLM09, LLM03, LLM05, LLM01)

### ss_enc — Encrypt embeddings at rest + in transit · `LLM09`
**Verdict: Full (at-rest/in-transit) / Emerging (in-use).**
- **OSS:** Google Tink (envelope encryption pre-DB), Vault Transit, Postgres pgcrypto/pg_tde, Redis TLS, Weaviate/Qdrant/Chroma (TLS+vol), Confidential Computing/TEE (Gramine+SGX).
- **Commercial:** Cloud KMS (AWS/GCP/Azure CMEK), MongoDB CSFLE/Atlas, Pinecone (managed TLS+at-rest+RBAC).
- *Gap:* In-use encryption (TEE) is porting-heavy. Otherwise mature.

### ss_acl — Tenant / namespace ACLs on the vector store · `LLM03`
**Verdict: Full (vector-DB-native).** This is the one control with genuinely AI-native, built-in tooling.
- **OSS:** Pinecone (namespaces+scoped keys), Weaviate, Milvus, Qdrant, Chroma, pgvector+Postgres RLS, MongoDB Atlas.
- *Gap:* Chroma OSS tenant ACL maturity `unsure`; Azure AI Search ACL still preview.

### ss_val — Index validation (screen docs for poison/injection) · `LLM05, LLM01`
**Verdict: Partial (composite).** No dedicated "vector-index validator"; you compose a document screener.
- **OSS:** Presidio / LLM Guard (injection+PII), garak/PyRIT (poison scans, OSS), OPA/Casbin policy on ingest.
- **Commercial:** Lakera Guard, HiddenLayer, Protect AI.
- *Gap:* Index-level *poison* detection is largely research-stage; injection screening is the mature half.

## 5. Supply Chain & Vulnerability (OWASP LLM04, LLM05, LLM08)

### sc_inv — Model / Vendor Inventory · `LLM04`
**Verdict: Partial (repurpose).** Mostly governance registries; auto-discovery of data flows is weak.
- **OSS:** Hugging Face Hub (model cards/registry), MLflow Model Registry, OWASP Dependency-Track (holds ML-BOMs).
- **Commercial:** ModelOp Evergreen, ServiceNow AI Control Tower, VerifyWise, MS Purview.
- *Gap:* Most are manual governance registries, not auto-discovered vendor catalogs. *ML-aware* inventory (model artifacts) limited to HF + ML-BOM tooling.

### sc_sbom — SBOM & Dependency Scan · `LLM04`
**Verdict: Partial (composite).** Software half is mature; model-weight half is emerging.
- **OSS:** cdxgen (reaches HuggingFace models; ML-BOM), Syft, Trivy, Grype, OWASP Dependency-Check, Dependency-Track.
- **Commercial:** Snyk, CycloneDX ML-BOM / Zeropath AI-BOM.
- *Gap:* cdxgen generates but doesn't CVE-scan; Trivy/Grype cover *software* (tokenizers, loaders) not weights. No single OSS tool covers weights+RAG-loaders+CVE end-to-end.

### sc_train — Training/Pretrain PII & Poison Scan · `LLM04, LLM05`
**Verdict: Partial (PII) / Emerging (poison).** PII scanning mature; **data-poisoning detection has no production tool.**
- **OSS:** Presidio, Cleanlab (label/quality errors), ModelScan (unsafe serialization), TrojAI (research).
- **Commercial:** AWS Macie, GCP DLP, HiddenLayer Model Scanner.
- *Gap:* **Biggest gap in the supply-chain set** — pre-train *poisoning* detection is research/labelled-data-quality only. PII tools scan text, not model artifacts or poisons.

### sc_cfg — Provider Config & Key Hygiene (DPAs, no hard-coded keys, kill-switch) · `LLM04, LLM08`
**Verdict: Partial (repurpose).** Key hygiene = mature; **provider kill-switch is a pattern, not a product.**
- **OSS:** HashiCorp Vault, LiteLLM, SOPS+External Secrets Operator, Cloud KMS.
- **Commercial:** Portkey, cloud Secrets Managers.
- *Gap:* Signed DPAs are contractual, not tool features. **No off-the-shelf "cut compromised provider" button** — implement at gateway (disable deployment) or secret layer (Vault `lease revoke`).

### sc_lic — License / Provenance Check · `LLM04`
**Verdict: Partial (repurpose).** Software SCA mature; model/dataset license + provenance is split.
- **OSS:** Hugging Face cards, ScanCode, ClearlyDefined, OSS Review Toolkit, sigstore/cosign+in-toto+SLSA.
- **Commercial:** FOSSA, Mend SCA.
- *Gap:* SCA tools don't classify *model-weight* licenses. Provenance/attestation (sigstore/SLSA) is the mature ML piece but addresses source attestation, not license type.

## 6. Detection, Alerting & Feedback (post-usage) (LLM01, LLM02, LLM06, LLM07, LLM09, LLM10)

### post_dlp — Semantic (LLM-based) Egress DLP · `LLM02`
**Verdict: Partial (composite).** The *inspector* model pattern is real; products exist but SaaS egress can defeat "separate instance" intent.
- **OSS:** Llama Guard 3/4, OpenAI Privacy Filter (open-weight, new), NeMo/GuardrailsAI (custom rails), Private AI.
- **Commercial:** Azure Content Safety PII, Lakera Guard (strong semantic, but SaaS egress), Private AI.
- *Gap:* **Exclude** PromptGuard/Rebuff here — they are prompt-injection tools, not PII/secret DLP. True "separate-instance inspector" requires deploying your own second model.

### post_emb — Embedding-exposure Detector · `LLM09`
**Verdict: Emerging / build. THE gap control.** No turnkey product detects "embeddings copied/queried by an untrusted party."
- **Partial signal:** Orca/Wiz/Prisma CSPM (catch *exposed* vector DBs), vector-DB RBAC + audit logs.
- *Gap:* Access-monitoring only; the semantic "copied to unexpected party" detection must be **built** (audit-log anomaly + egress monitoring of the VDB).

### post_anom — Anomaly & Leak Detection · `LLM06, LLM02`
**Verdict: Full (components).** Mature pieces; integration is the work.
- **OSS:** LangSmith/Langfuse/Helicone/AgentOps (token-volume), Datadog/Splunk/Elastic, Nightfall/TruffleHog/GitGuardian/detect-secrets (secret/PII leak).
- **Commercial:** same + cloud native.
- *Gap:* None on tooling; you wire volume + secret/PII leak signals into one detector.

### post_drift — Drift & Feedback Loop · `LLM07`
**Verdict: Full.** Mature eval/observability.
- **OSS:** Evidently, Deepchecks, Giskard, Arize Phoenix, WhyLabs, Arthur, Fiddler.
- **Commercial:** same + Langfuse/LangSmith score+annotation (closes the feedback loop best).
- *Gap:* None material; LLM07 misinformation is governed here, not per-request.

### post_alert — Audit → SIEM Alerting (immutable traces to SOC/IR) · `LLM10, LLM02`
**Verdict: Partial (composite).** Plenty of forwarders; immutability lives in the backend you choose.
- **OSS:** OpenTelemetry Collector exporters, Vector, Fluent Bit/Fluentd, Falco, Loki→OnCall.
- **Commercial:** Cribl, Splunk HEC / Elastic Agent / Sentinel connectors.
- *Gap:* These forward; true immutability = WORM/CloudTrail-style store you bolt on.

### post_rt — Red-team & Review Queue (human review of near-miss/injection events) · `LLM01`
**Verdict: Partial (composite).** Scanning mature; unified AI-incident review queue nascent.
- **OSS:** garak, PyRIT, Promptfoo, CyberSecEval (scanners); LangSmith/Langfuse annotation queues.
- **Commercial:** Lakera (injection detect+log), HumanLayer (HITL review).
- *Gap:* No single purpose-built AI-incident review product; compose scanner + annotation queue.

## 7. Agent tool & runtime controls (OWASP Agentic ASI01–ASI10; secondary LLM)

### agent — Orchestrator that plans but CANNOT call tools directly · `ASI01/02; LLM03`
**Verdict: Partial (architecture, not a feature).** No framework enforces isolation by default — you architect the split.
- **OSS:** LangGraph (interrupt/checkpointer pauses before tool node), AutoGen, CrewAI, MS Agent Framework/Semantic Kernel, Google ADK, Pydantic AI, SmolAgents, Anthropic Agent SDK.
- *Gap:* Planner emits typed calls; a *separate hardened executor* runs them. Isolation is opt-in/by-design, not a toggle.

### proposal — Structured Action Builder (typed schema-bound action) · `ASI02/09; LLM03/10`
**Verdict: Partial (composite).** Typed schemas exist; **"expected side effects" field is not native to any tool** — you extend the schema.
- **OSS:** Pydantic/Pydantic AI, Instructor, MCP tool `inputSchema`, LangGraph ToolCall, jsonschema/ajv, Cerberus.
- **Commercial:** Anthropic/OpenAI tool-use JSON Schema.

### registry — Tool / MCP Allowlist · `ASI02/04; LLM04`
**Verdict: Partial (composite).** MCP-native options exist; generic tool registry = policy-encoded. **The strongest single-tool enforcement candidate is [nono](https://nono.sh)** (Sigstore team) — kernel-enforced micro-sandboxes that pull *signed* tool profiles from registry.nono.sh, collapsing registry + param + credential + approval + audit + proxy into one agent-agnostic OSS tool (see `proxy`/`credential`/`audit` rows).
- **OSS:** **nono** (capability broker + signed profile registry + per-invocation sandbox), ToolHive (isolated MCP containers + capability model), MCP Registry spec+Smithery, mcp-proxy, FastMCP, OPA/Casbin (encode allowlist).
- **Commercial:** Kong/Apigee, Cloudflare MCP, Heroku MCP.
- *Gap:* Registration ≠ authorization; you add the allowlist *policy*. Nono's signed profiles + argv policy cover the allowlist natively but still need your risk→authorization mapping.

### identity — Identity & Delegation Context (OIDC / workload identity) · `ASI03/07; LLM02/03`
**Verdict: Full (repurpose).** Standard IdP/workload-identity tooling.
- **OSS:** Keycloak, SPIFFE/SPIRE, Vault, Auth0 FGA (OpenFGA).
- **Commercial:** Okta/Auth0, Azure Entra.

### param — Parameter & Schema Validator (reject injection/traversal/out-of-bounds) · `ASI02/05; LLM01/10`
**Verdict: Partial (composite).** Typed validation mature; *security* validation (injection/traversal) needs a guardrail lib or rules. **nono enforces this at the kernel layer** via argv policy (caller + arguments) before any tool executes — stronger than app-level schema validation because the process tree is Landlock/Seatbelt-restricted, not merely checked.
- **OSS:** **nono** (argv policy + capability broker), Pydantic, Zod, jsonschema/ajv, GuardrailsAI (RAIL: injection/out-of-bounds), Rebuff, custom path canonicalization.
- *Gap:* Base validators are not security-focused; you add injection/traversal rules. Semgrep fit `unsure`. Nono covers argv/command policy but not full JSON-schema semantic validation of complex params.

### pdp — Tool Policy Decision Point (ABAC) · `ASI02/03; LLM03`
**Verdict: Full (repurpose).** Mature policy engines.
- **OSS:** OPA, Cerbos, OpenFGA, AuthZed/SpiceDB, Casbin, Permit.io/Aserto.
- **Commercial:** AWS Verified Permissions.

### risk — Action Risk Classifier (destructive/financial/privileged/bulk-export) · `ASI02/09; LLM03`
**Verdict: Partial (mostly custom).** Few turnkey products; mostly LLM-judge + rules.
- **OSS:** OPA/Casbin rules, NeMo Guardrails (risk rails), custom LLM "risk judge".
- **Commercial:** Lakera Guard, Lasso/HiddenLayer/Protect AI (verify per vendor — `unsure`).
- *Gap:* Semantic risk classification is largely a build; static rules cover the obvious cases.

### approval — Approval Gate (informed, time-bound human approval) · `ASI01/02/09; LLM03`
**Verdict: Partial (composite).** Purpose-built HITL exists but you wire risk→approval trigger + timeout. **nono provides this inline** — any invocation matching no argv rule pauses for a human approve/deny/timeout decision, then runs inside a scoped sandbox.
- **OSS:** **nono** (inline human-approval on out-of-policy calls), HumanLayer (purpose-built), LangGraph `interrupt()`, Temporal (signal+timers), Slack/email approve buttons.
- **Commercial:** MS Agent Framework + Azure Approval, Jira ticketing.

### credential — Credential Broker (short-lived, scoped creds) · `ASI03/05; LLM02/03`
**Verdict: Full (repurpose).** Mature STS/dynamic-secret infra. **nono is the closest to the control's *ideal* — it never exposes the real credential to the agent at all:** the supervisor holds the secret, injects a phantom token, and swaps in the real credential only at the L7 proxy boundary, zeroising on exit.
- **OSS:** **nono** (phantom-token boundary injection, secret never enters child), HashiCorp Vault (dynamic secrets), Boundary, OIDC token exchange (RFC 8693) + your broker.
- **Commercial:** AWS/GCP/Azure STS, CyberArk/strongDM/Teleport, IAM Roles Anywhere.

### txn — Transaction & Idempotency Guard (limits, dedupe, dry-run, rollback) · `ASI02/08; LLM03/06`
**Verdict: Partial (composite).** Durable-orchestration infra covers it; you model the transaction.
- **OSS:** Temporal, Cadence, DB transactions + Outbox, Redis limiter, LangGraph checkpointer, idempotency-key pattern.

### proxy — Tool Execution Proxy / Sandbox / Egress Gateway · `ASI02/05/07; LLM03/10`
**Verdict: Partial (composite) — but [nono](https://nono.sh) collapses the enforcement spine into one OSS tool.** Isolation primitives exist; tool-semantics-aware proxy is MCP-only today *except nono*, which brokers every tool call through a kernel-enforced micro-sandbox (Landlock/Seatbelt) with argv policy, capability scoping, and an L7 egress proxy.
- **OSS:** **nono** (kernel-enforced per-invocation sandbox + argv policy + L7 proxy + credential boundary — covers `proxy`+`param`+`credential`+`approval`+`audit` together), ToolHive (MCP isolated containers), E2B (Firecracker microVM), gVisor, Docker/Firecracker/Kata, Envoy/Istio egress, Squid.
- **Commercial:** Modal, Northflank.
- *Gap:* Generic egress gateways lack tool-semantics awareness; ToolHive is the only MCP-native. Nono adds agent-agnostic kernel sandboxing on top, but still omits the *operational* spine (`txn`/`governor`/`resilience`/`risk`/`kill`).

### result — Tool Result Validator (schema + content filter on untrusted tool output) · `ASI01/06/07; LLM01/02/10`
**Verdict: Partial (composite).** Validates *schema* well; *content/poison* filtering on tool output is a guardrail lib + policy job. **nono changes the trust model**: because the agent never holds the real credential and every tool runs in an invocation-scoped sandbox, tool output is returned across a supervisor boundary that can strip/validate before the agent sees it — but content-level poisoning detection still needs GuardrailsAI/OPA on top. *(see injection appendix for tool-output poisoning candidates)*

### governor — Runtime Governor (rate/concurrency/step/token/time/cost budgets) · `ASI02/08; LLM06`
**Verdict: Partial (composite).** Gateway covers rate/token/cost; *step* cap needs the agent framework.
- **OSS:** LiteLLM Proxy (budget+duration+rpm/tpm+max_parallel), Portkey core, Helicone, LangGraph (`recursion_limit`), AutoGen/CrewAI (`max_round`/`max_iter`), OPA.
- **Commercial:** Portkey, Cloudflare AI Gateway, LangSmith, AWS Bedrock, AgentOps (`unsure` on hard-budget enforcement).
- *Gap:* No single tool does all five budget dimensions; compose gateway + framework + OPA.

### resilience — Resilience Controller (deadlines, retries, circuit breakers, fallback) · `ASI08; LLM06`
**Verdict: Full (repurpose).** Standard resilience libs/infra.
- **OSS:** Temporal, Tenacity, resilience4j, Polly, Envoy/Istio, LangGraph retries.
- *Gap:* None; almost entirely generic infra.

### audit — Append-only Audit/Trace Pipeline · `ASI08/09/10; LLM02/06`
**Verdict: Partial (composite).** Observability tools trace everything; **true append-only needs a WORM/CloudTrail-style backend — except [nono](https://nono.sh), whose per-invocation audit is hash-chained into a SHA-256 Merkle root, i.e. tamper-evident by construction** (the closest off-the-shelf match to the WORM ideal).
- **OSS:** **nono** (Merkle-rooted, tamper-evident audit of every supervisor crossing), Langfuse, AgentOps, Helicone, OpenTelemetry, MLflow, OpenObserve/Loki/ClickHouse.
- **Commercial:** LangSmith, AWS CloudTrail (WORM via S3 Object Lock).
- *Gap:* Most LLM-observability DBs are mutable; bolt on WORM for immutability. Nono's trail is verifiable but covers tool-execution events, not full proposal-lifecycle metadata.

### kill — Kill Switch & Incident Control · `ASI08/10; LLM03`
**Verdict: Partial (composite).** **No dedicated "AI kill switch" product** — compose from the below. **nono contributes containment**: each sandbox is destroyed on invocation exit, so a compromised tool call cannot persist or spawn outside its boundary; combined with Vault revoke + run cancel this is a credible incident response.
- **OSS:** **nono** (per-invocation sandbox destroyed on exit — limits blast radius), Vault lease revocation, ToolHive stop/disable, Temporal cancel, Kubernetes network policies, framework stop (LangGraph `.stop()`/Anthropic stop/OpenAI cancel), Envoy circuit break.
- **Commercial:** Lakera Guard / PANW AI Runtime Security (policy block/quarantine).
- *Gap:* Credential revoke + run cancel + egress cut must be wired together per-component; nono stops the *sandbox*, not an in-flight model generation.

## Cross-cutting findings

1. **No single product covers the full control set — but one tool now covers the *enforcement spine*.** Realistic stacks:
   - *Private-data exposure:* Presidio/Private AI (redaction) + vector-DB ACLs (ss_acl) + gateway (tok_gate/tok_rl/rag_out) + a **separate** inspector model (post_dlp) + observability (post_anom/post_drift) + SIEM forwarder (post_alert).
   - *Agent loop:* the **enforcement spine** (`registry`+`param`+`credential`+`approval`+`proxy`+`audit`+partial `kill`) is now addressable by a **single OSS tool — [nono](https://nono.sh)** (kernel-enforced per-invocation sandbox, signed profiles, phantom-token credential boundary, Merkle audit, sandbox-destroy containment). The **operational spine** (`txn`/`governor`/`resilience`/`risk`) and the data-exposure + supply-chain layers remain composite/multi-tool. So: not "assemble 5 tools for the loop" — assemble nono + a transaction/resilience layer (Temporal) + the content guardrails (NeMo/GuardrailsAI) + your data/supply-chain stack.
   - *Supply chain:* cdxgen (ML-BOM) + Trivy/Grype (CVE) + Dependency-Track (monitoring) + Presidio/Macie/DLP (corpus PII) + sigstore/SLSA (provenance) + HF/ModelOp (license+inventory). **Cleanlab is the only poison-adjacent control.**

2. **AI-native vs repurposed infra.** Genuinely AI-native: vector-DB tenant ACLs (ss_acl), LLM gateways (LiteLLM/Portkey), MCP security (ToolHive, **nono** — kernel-enforced agent sandbox), agent observability (LangSmith/Langfuse/AgentOps/Helicone), HumanLayer, Lakera. Everything else repurposes OPA/OpenFGA/Keycloak/Vault/K8s/Envoy/SIEM.

3. **The weakest-covered controls (build, don't buy):** *(updated — nono removes `kill` and `agent`-isolation-in-enforcement from this list; the genuine build gaps are now data/supply-chain + operational)*
   - `post_emb` (embedding-exposure detector) — **must build**; only CSPM + VDB audit-log signal exists.
   - `sc_train` pre-train *poisoning* — **no production tool**; research-stage only.
   - `agent` isolation — an **architecture**; nono makes the *tool-execution* half enforceable, but the planner/executor split is still a design decision.
   - `risk` classification — **mostly custom** LLM-judge + rules (nono handles argv/command policy, not semantic risk of the *action*).
   - *Downgraded:* `kill` is no longer "no product" — nono's per-invocation sandbox-destroy + Vault revoke + Temporal cancel form a credible containment story, though no single "AI kill switch" button exists.

4. **"Separate-instance inspector" is the load-bearing rule.** `post_dlp` and `an_dlp` rely on a DLP/inspector model *disjoint* from the app LLM. SaaS DLP (Lakera/Nightfall) technically re-introduces egress; for the repo's threat model, self-hosted Presidio / open-weight Llama Guard / Private AI is the faithful implementation.

5. **Honest "unsure" flags carried from research:** OpenAI Privacy Filter license & on-prem viability; Private AI on-prem terms; Llama Guard exact PII/secret coverage; vLLM per-key logprob suppression; AgentOps hard-budget enforcement; Permit/agent-specific primitives; Azure AI Search ACL GA status; Lasso/HiddenLayer/Protect AI risk specifics; HumanLayer deep red-team-queue features; Semgrep runtime param-fit.

6. **"Nvidia's vs Nono.sh" are orthogonal, not competitors.** This came up via an X post comparing the two; the comparison only makes sense if you understand they defend *different boundaries* of the same system:
   - **NVIDIA → content boundary (`04` diagram).** "Nvidia's" here means **NeMo Guardrails** (NVIDIA's open-source LLM guardrail library). It operates *on the language path* — input rails (jailbreak/injection), output rails (`an_out`), retrieval rails (`rag_scr`/`ss_val`), execution rails (`param`/`result`), and risk rails (`risk`). Already catalogued under those controls. (If the poster meant NVIDIA Morpheus instead, that's a network-threat-detection framework — less LLM-specific; NeMo is the clear LLM-security fit.)
   - **Nono.sh → tool-execution boundary (`05` diagram).** nono operates *on the action path* — does the agent's tool call escape its sandbox? is the real credential exposed? is the call scoped? That's `registry`/`param`/`credential`/`approval`/`proxy`/`audit`/`kill`. It does **not** inspect prompt text or model output for jailbreaks/toxicity.
   - **They stack, they don't overlap.** Best practice is NeMo on the content path + nono on the tool-execution path. Together they cover far more of the loop than either alone, but neither touches the data-exposure `04` store controls (`ss_enc`, `ss_acl`, `post_emb`) or the supply-chain `sc_*` layer. The post's implicit "which is better?" framing is the wrong axis — the real question is which boundary you're undefended on.

### result — Tool Result Validator (schema + content filter on untrusted tool output) · `ASI01/06/07; LLM01/02/10`
| App | Tag | Fit note / gap |
|---|---|---|
| **ToolHive** (Stacklok) | OSS | Runs MCP servers in isolated containers; Gateway applies org policies + network/egress isolation. MCP-native. Gap: policy/network-level, not deep payload content inspection (`unsure` on fine-grained result filtering). |
| **MCP Guardian** (EQTY Lab) / **mcp-proxy** / **Pro-vi/mcp-filter** | OSS | Security proxy/gateway → tool-surface filtering, audit logs, per-key allowlist (verified this run). Gap: tool *surface* control, not semantic result-poisoning detection. |

| **GuardrailsAI / LLM Guard** | OSS+Comm | Content/schema validation + PII/secrets screening on tool output before the agent acts. |

*Gap (the important one):* **Most agent frameworks treat tool/function-call results as trusted

(ToolHive / MCP Guardian / mcp-proxy / mcp-filter) and an explicit OPA/guardrail gate treat
**tool output as untrusted** before it influences the next step. Schema validation is mature;
**content/poison filtering on tool output is the immature half** — you build the validator.

### One-line summary for this cluster
Detection of injected instructions is **mature** (Lakera, Prompt Shields, PromptGuard, Rebuff,
NeMo/Guardrails, Llama Guard, Azure); **prevention** requires wiring the detector to a gate or
policy engine (OPA/Casbin, NeMo rails). Microsoft Prompt Shields adds **Spotlighting** (marks
untrusted content) and `documentsAnalysis` for corpus screening — but is Azure-only. The
distinctive gap is `result`: tool/function-call **output** poisoning is under-served because
frameworks trust tool results by default — MCP-security proxies + an explicit validator are the
current answer. **Detect vs prevent:** PromptGuard, Rebuff, Vigil, garak, Llama Guard = detect/score
(block by wrapping); Lakera, Prompt Shields, NeMo/Guardrails, ToolHive/MCP proxy, OPA = enforce/prevent.
